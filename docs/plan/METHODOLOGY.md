# Mathematical and experimental methodology

This is the required depth and decision framework, not a finished theoretical chapter or an
accepted implementation specification. Gillis is the main source; the supporting papers are
mapped in [LITERATURE](../research/LITERATURE.md). The objective and solver remain open.

## 1. Notation and model

Use a consistent orientation: $A\in\mathbb{R}_{\geq0}^{m\times n}$ has one sample per column,
$W\in\mathbb{R}_{\geq0}^{m\times r}$ contains components and
$H\in\mathbb{R}_{\geq0}^{r\times n}$ contains their weights. The model is $A\approx WH$;
$\operatorname{rank}(WH)\leq r$. State what rows, columns and the inner dimension mean for the
chosen data. If code stores samples by row, explain the transpose explicitly.

Explain additive combinations, the cone generated by the components, low-rank compression,
the relation to truncated SVD/PCA and the limits of interpretability. Nonnegative factors
need not be unique, sparse or semantically meaningful.

## 2. Objective and optimization

A reference formulation for discussion is

$$
\min_{W,H\geq0} f(W,H)=\frac12\lVert A-WH\rVert_F^2.
$$

This example does not select the final objective. Explain its error assumptions and contrast
it with the generalized KL formulation if relevant. Derive the gradients for this example:

$$
\nabla_W f=(WH-A)H^T,\qquad \nabla_H f=W^T(WH-A).
$$

Show why fixing one factor gives a convex nonnegative least-squares subproblem, while the
joint problem is nonconvex. Derive the first-order KKT conditions: primal nonnegativity,
nonnegative gradient entries at a stationary point, and complementary products
$W\odot\nabla_W f=0$ and $H\odot\nabla_H f=0$. Explain why these are not a global-optimum
certificate for the joint problem.

Treat scale/permutation ambiguity explicitly: for a positive diagonal $D$,
$(WD)(D^{-1}H)=WH$. Consequently individual factors cannot generally be validated by exact
entrywise agreement with another run. Normalization changes factor interpretation and must
preserve the reconstruction when it is intended only to fix scale.

## 3. Derivation of the chosen algorithm

After choosing a solver, derive its actual updates from the objective rather than merely
quoting pseudocode. Explain the alternating order, dimensions, initialization, nonnegativity,
computational work and stopping rule. For multiplicative updates, if selected, cover their
connection to a scaled gradient step and the auxiliary-function argument for nonincrease.

Separate three statements: objective nonincrease, convergence/stationarity of iterates and
global optimality. State exactly which assumptions support a claim. Discuss zeros that stay
zero, zero denominators, inactive components, finite precision and any safeguard actually
used by code; adding epsilon changes the implemented rule and needs an explanation.

Include at least one small worked iteration or independently checkable numerical example.
A comparison with another algorithm is justified by a question, not required by this plan.

## 4. From the real problem to a matrix

Before choosing data, write the question and what a useful component/weight would mean.
Record the source, license/access, version or checksum, sample/features, missing values,
preprocessing and matrix orientation. Explain why the representation and objective make
sense for those measurements. Do not silently shift negative data merely to make NMF run.

If the application is clustering, define the conversion from weights to cluster assignments,
including normalization and ambiguous assignments. A topic/component representation and a
hard partition are different outputs. Weights need additional assumptions to be probabilities.

## 5. Implementation verification

Choose a supported Python environment and dependency lock when implementation begins.
Keep the numerical method callable independently of a notebook or real dataset. Cover input
validation, nonnegativity and finite output, a small known reconstruction, appropriate
objective behavior, stopping and edge cases of the selected method.

Use justified tolerances and independent calculations. Where a library is used as a reference,
match objectives/settings and account for nonuniqueness. Tests/CI use small synthetic or
redistributable fixtures and do not require full data downloads or a paid service.

## 6. Experiments and evaluation

Agree questions, ranks, seeds/initializations, stopping settings, baseline, metrics and compute
budget before the main runs. Choose domain evaluation after the application is known; no
single clustering metric or classification split applies to every NMF problem.

Every reported run must identify:

- Input source/version or checksum and preprocessing/settings.
- Code revision and dirty state; before a commit exists, record that fact and identify the
  working snapshot rather than inventing a revision.
- Python/dependency environment, rank, objective, solver and all numerical settings.
- Random seed/initialization, stopping reason, iteration count and objective/error.
- Domain metrics/interpretation and any failure or nonconvergence; hardware/thread settings
  and timing scope when reporting speed comparisons.

Keep raw/bulk outputs local, with a run ID. Preserve enough metadata and small curated
tables/figures for each reported claim. Do not overwrite the only record of a reported run.
Discuss stability across the agreed seeds/ranks, interpretability and limitations separately
from reconstruction quality. If there is a held-out evaluation, fit preprocessing on its
training/development portion and keep final evaluation out of tuning.

## 7. Written and oral explanation

The seminar connects problem, matrix, objective, derivation, code, experiments and conclusions.
Cite theoretical sources by section/theorem where possible. Trace project figures to the
generating run and distinguish them from borrowed illustrations. The presentation uses the
same definitions and evidence. All three members practice explaining the full chain.
